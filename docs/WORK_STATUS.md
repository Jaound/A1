# 최신 작업 — 플레이 UI R2 진행 중

**KX 임무 회귀 원인 추적:** `MarkedHit_KU_Mission.log`의 실패 직전 공격 `1258`은 아군 항모 `OVShip_0`의 `Weapon_1`이 적 항모 `OVShip_6`에 명중했고, `OVDamage event=658`은 하부 장갑 `Armor_F5_R1_C1`, 2층 중앙 `D2_X2_Y1`, 선체 피해 39, `wreck=1`로 기록됐다. `MakeTestLayout`에서 3층 함체의 코어는 `D2_X2_Y1`이고 `ApplyWorldHit`은 파괴된 상하 장갑/시설 뒤로 2층을 관통시킨다. 따라서 새 상자 접촉면으로 하부 관통·코어 파괴가 발생한 것이 목표 완파의 직접 경로라는 근거가 있다. 다만 상자 근사나 자동 교전 명령 중 어느 쪽을 조정해야 하는지는 다른 각도·기존 규칙·사용자 조작으로 추가 검증해야 하며, 피해를 일괄 낮추거나 회귀 검사를 약화하지 않는다. 도면 장착과 후보 상자는 기본 비활성으로 유지한다.

**KW 선체 충돌·피격 검증 (부분 완료, 기본 적용 보류):** KQ의 14종 302개 상자를 `GenerateHullCollisionData.py`로 런타임 데이터에 생성하고 도면 장착 시험 스위치와 연결했다. UE 실제 `RequestFire`와 발사체 시뮬레이션에서 표시점 129개 각각에 빔·포탄을 수직/사선 두 방향으로 발사한 516/516개 포탑 피격 사례가 통과했다(`MarkedHit_KT_Automation.log`). 14종 × 상하좌우 × 빔/포탄 112사례는 장갑·시설 슬롯·선체 피해 연결까지 통과했다(`MarkedHit_KW_HullDamage.log`). 이는 고정 2방향/4방향 시험이며 모든 각도·표면·성능을 보장하지 않는다. 선체별 후보와 표시점은 기존 데이터로 남고 시험 스위치 `ov.Calibration.MarkedMounts 1`로 적용한다. 기본값을 1로 둔 KU 코드의 전체 자동 121/121, [D116 PIE 79/79](validation/PlayUIR2/KU_D116_API.json), [2C PIE 77/77](validation/PlayUIR2/KU_2C_API.json)이 통과했다. 그러나 [통합 임무 대표 2사례](validation/PlayUIR2/KU_Mission_API.json)는 19검사 중 종단 나포·회수 검사에 실패했다. 같은 시드의 이전 KN 성공에서는 강습선 진입 후 회수됐지만 KU에서는 쉴드 제거 약 150.8초, 강습 출발 후 목표가 약 156.5초에 완파돼 진입 전에 패배했다. 피해 수치·체력을 인위적으로 조정하거나 검사를 약화하지 않았으며 기본 스위치를 0으로 되돌렸다. 재설계 시 실제 공격 궤적·포탑/선체/시설 명중 및 목표 완파 원인을 비교하고 플레이어 수동 사격·기발사 공격·내부 아군 보호를 보존해야 한다. F6 `OVCalibration::Start`는 공격 무장만 등록하며 노란 PD 장착/등록이 누락돼 별도 해결이 필요하다. 최종 기본값 KV 빌드 성공·전체 자동 121/121, 이후 시설 슬롯 확인만 강화한 KW 빌드와 해당 112사례 성공. [단일 비렌더 API 시간 비교](validation/PlayUIR2/KU_충돌후보_API시간비교.json)는 일반 장면 14.705→18.583ms, 혼성 22.405→25.686ms/게임초이며 프레임 성능 보장이 아니다. 원본 3D 무장 9종과 강습선 수정은 미완료/제외, 직접 화면·입력·패키징·대규모 성능 미검증. 기존 사용자 UI 미커밋 3파일은 보존했다. 다음: 통합 임무의 목표 완파 원인을 정확히 계측해 합당한 전투/임무 해결책을 적용하고 추가 방향·성능 회귀와 F6 PD 등록을 검증한 뒤 기본값을 켠다. 이어 원본 무장별 가동부·포구·재질·접합을 구현·검증한다.

**KQ 선체별 충돌 후보 (미적용):** `BuildMarkedHullCollisionCandidates.py`로 사용자 표시가 있는 14종 원본 선체에서 각 최대 27개의 충돌 상자 후보를 제작했다([후보·FBX 해시](validation/PlayUIR2/KQ_선체충돌_후보.json)). 훈련에 사용하지 않은 수직 표면 표본 2,092개 중 2,065개에서 상하 양 끝이 상자에 포함됐으며 27개는 누락됐다. `AuditMarkedHullCollisionCandidates.py`의 단순 표시면 수직 입사 기하 계산에서는 129개 표시점 중 상자가 무장 피격 구를 먼저 가리는 경우가 0개였다([기하 검사](validation/PlayUIR2/KQ_선체충돌_기하검사.json), 재실행 일치). 이는 Blender 표면 샘플과 단일 방향 기하 비교이고 **UE 실제 공격·포탄·장갑·시설·사선·후방·성능 검증이 아니다.** 후보는 게임에 적용하지 않았고 도면 장착의 기본 스위치는 여전히 꺼져 있다. 다음은 UE 실제 빔/고속 포탄의 표시 무장 명중과 선체·장갑·시설 경로, 누락된 표본과 측면/사선, 원본 OBB 대비 전투·성능을 14종에 검증하고 수정하는 것이다. 원본 3D 무장 9종 적용은 미완료다.

**KP 길이 변경·도면 장착 시험 (부분 완료):** 원본 선체 메시 실제 X 길이를 기준으로 강습선을 제외한 15종에 소형:중형:대형:초대형 1:4:16:32를 적용했다. 수송선은 D119에 따라 중형 크기이며 강습선은 이번 범위에서 제외해 기존 크기를 유지한다. 함체 속도·피해 수치를 변경하지 않았다. 확대된 항공모함이 겹치지 않도록 F7 혼성 장면과 통합 임무의 시작 높이를 분리하고 기존 포드 거리 제한은 유지했다. 도면 일반/전용/PD 슬롯과 기존 장비 ID를 연결하고 좌우 PD 사각·전용 슬롯 프로필 제한을 구현했다. 사용자 도면의 방공함 일반 슬롯은 하나여서 **시험 모드에서만** 기존 공격 무장 두 개 중 하나만 기본 장착한다. 수송선은 도면 표시가 없어 기존 PD를 유지한다. 일반 슬롯의 서로 다른 무기 계열 교체 UI/동작은 아직 미구현이다. 기존 OBB 내부에 반지름 18의 피격 구가 완전히 가려지는 표시점이 95/129개여서([위험 목록](validation/PlayUIR2/KO_선체상자_무장피격_위험.json)) 도면 장착은 **기본 비활성**이다. `ov.Calibration.MarkedMounts 1` 후 F6/F7을 다시 시작하면 시험할 수 있으나 포탑 피격이 잘못될 수 있다. 기존 포탑·기능을 보존하기 위한 시험 스위치이며 완료 판정이 아니다. `MarkedMount_KP_Build.log` 빌드 성공, `MarkedMount_KP_Automation.log` 자동 119/119(시험 슬롯 연결·전용 제한·측면 PD·15종 길이·장면 간격 포함). 최신 기본값 PIE API는 [D116 79/79](validation/PlayUIR2/KP_D116_API.json), [2C 77/77](validation/PlayUIR2/KP_2C_API.json). 도면 장착 기본 활성화 상태의 이전 KN 코드는 [2C 77/77](validation/PlayUIR2/KN_2C_API.json), [통합 임무 대표 2사례 24/24](validation/PlayUIR2/KN_MissionSmoke_API.json)이나 이후 전용 프로필 제한/기본 스위치가 추가돼 최종 코드 검증으로 보지 않는다. KM 혼성 장면 사거리 문제는 이후 시작 높이 수정으로 해결했고 [실패 증거](validation/PlayUIR2/KM_2C_API.json)는 보존한다. 전체 29사례는 장시간 수행 중 중단되어 미완료다. 사용자의 UI 미커밋 3파일이 빌드에 포함됐지만 커밋에서 제외한다. **남음:** 14종별 선체 표면 근사 충돌을 만들어 모든 표시 포탑의 외부 빔·고속 투사체 피격과 선체/장갑/시설 피해·기존 전투량·성능을 검증한 후 도면 장착을 기본 적용한다. 원본 무장 9종의 가동부 분리·피벗·재질·포구·선체 간섭·전용 대함미사일 모델을 실제로 적용해야 한다. 현재 임시 무장 모델을 원본 완료로 표기하지 않는다. 원본 모델 전체 적용, 직접 화면 입력·장면 시각 확인, 패키징과 대량 성능은 미검증이다. 다음은 기존 PC14 27상자 시험을 토대로 선체별 충돌 후보와 정확도/전투 회귀 검증을 확장한다.

**KE 도면 후보 데이터와 UE 표면 확인:** 사용자가 서로 다른 면의 표시는 모두 독립 슬롯으로 확정했다. `OVMarkedSlots`에 함종·면·색상·영역별 ID를 가진 후보 129개를 생성 도구와 함께 추가했다. 초계함 4개와 나머지 표시가 있는 13종 125개를 실제 UE 원본 정적 메시의 LOD0 삼각형과 대조했다. 총 129/129개가 투영 방향 기준 1cm 이내이며 최대 0.9431cm다([검사](validation/PlayUIR2/KE_표시점_UE표면검사.json)). 이 검사는 슬롯 중심 표면 좌표만 확인하며 포탑 접합·충돌·발사·피격은 검증하지 않는다. `MarkedSlots_KE_Build.log` 빌드 성공, `MarkedSlots_KE_Automation.log` 116/116; 기존 미커밋 UI 3파일이 빌드에 포함됐지만 이번 커밋에서는 제외한다. 아직 후보를 실제 함선 장착 데이터에 연결하지 않았다. 방공함은 기존 공격 무장 2개지만 표시된 일반 슬롯은 1개이고 수송선은 표시가 없다(기존 PD 2개). 강습선은 이번 범위에서 제외한다. 다음: 실제 장비와 빈 슬롯을 분리하고 도면 슬롯에 전용·일반·PD를 연계한다. 선체 OBB보다 안쪽인 슬롯이 포탑 피격보다 먼저 선체에 맞는 문제를 검증·수정하고, 원본 무장·길이 1:4:16:32와 장면 간격·카메라를 적용한 후 빌드·전투·PIE·직접 화면을 각각 검증한다.

**측면 장착 기초 (KB, 진행 중):** 사용자가 서로 다른 면에 표시한 위치는 각각 독립 슬롯이라고 확정했다. 무장 정의에 선택적인 선체 로컬 장착면 법선을 추가하고, 일반 공격 무장의 발사 사각·고정 미사일 포구와 초기 경로·측면 임시 형상 회전에 연결했다. 법선이 없는 기존 데이터는 기존 상하 규칙을 유지한다. 원본 BF120 시험 외형은 측면을 지원하지 않아 기존 임시 형상으로 대체한다. `SideMount_KB_Build.log` 성공, `SideMount_KB_Automation.log` 113/113(좌측 허용·반대편 차단·측면 포구 및 기존 상하 회귀). 기존 사용자 UI 미커밋 3파일이 빌드에 포함되었다. **아직 도면 슬롯을 게임에 적용하지 않았고**, 측면 PD 사각·원본 무장 전체·함선 길이 1:4:16:32·표면 피격/장착 검증은 미완료다. 서로 다른 면의 표시를 중복 제거하면 안 된다. 강습선은 사용자 지시대로 이번 단계에서 제외한다. 다음은 PD에도 면 방향을 연결하고 사용자 3D 후보를 UE 메시에 검증해 독립 슬롯/기존 무장 모듈을 연결한 뒤 원본 무장과 길이·카메라·교전 범위를 함께 완성한다.

**PC14 무장 3방향 실사격 (HD):** 표면 장착 후보를 기존 단일 OBB, 초기 5상자, 측정 기반 27상자와 비교했다. 빔·포탄 각각 상방/전방/측면에서 실제 발사한 시험에서 27상자는 세 방향 모두 무장에 닿았다. 기존 OBB는 세 방향에서 함체가 먼저 맞았고, 초기 5상자는 상방만 무장에 닿고 전방/측면은 함체가 가렸다. 최초 HC 검사는 5상자의 세 방향 성공을 잘못 기대해 실패했으며, 이를 숨기지 않고 관찰된 가림을 명시하는 비교로 수정했다. `PlayUI_R2_HD_Build.log` 성공, `PlayUI_R2_HD_Automation.log` 전체 자동 102/102. 특정 단일 장착점·세 직선 방향의 시험으로 하부·사선·전체 장갑/시설과 대량 성능은 남아 있다. 기본 모델 적용은 아직 하지 않았다.


**PC14 측정 기반 충돌 후보 (HA/HB):** UE의 1,073개 수직 표본 중 Y 10cm 간격으로 27개 상자를 구성하고 Y 5cm 중간 표본을 별도로 비교했다. HB 빌드 성공, 전체 자동 102/102. 측면·하부·비스듬한 피격, 내부 장갑/시설, 충돌 형상 성능과 직접 입력은 미검증이다. 기본 장면에는 적용하지 않았다.


**PC14 UE 표면 추가 측정 (GY/GZ):** 반입된 시험 메시의 UE 렌더 삼각형을 상하 수직 레이로 직접 검사하는 자동 시험을 추가했다. **시험용 복합 함체 충돌 (GW/GX):** `CombatHullBoxes`가 비어 있으면 기존 단일 전투 OBB를 그대로 사용한다. 시험용으로만 기존 OBB 내부의 여러 상자를 명시하면 공격은 가장 먼저 닿은 상자/무장을 사용하고, 패인 면의 장갑 구분은 충돌 법선을 따른다. 선택과 아군 사선 차단의 기존 OBB는 변경하지 않는다. 상자는 양수·유한·기존 OBB 안·최대 32개로 검증한다. PC14 상부 한 지점을 시험값인 다섯 상자로 근사했을 때 기존 형상에서 가려지던 무장을 실제 빔/포탄이 다시 명중했다. 함체 표면 전체를 측정해 만든 최종 충돌 형상은 아니다. `PlayUI_R2_GW_Build.log` 성공, 전체 자동 101/101, [PC14 시험장 API 13/13](validation/PlayUIR2/GW_PC14충돌상자_API.json), [2B API 50/50](validation/PlayUIR2/GX_2B회귀_API.json). 추가 형상 시각 [렌더](validation/PlayUIR2/GW_PC14충돌상자_1280.png). 실제 마우스 입력·패키징·다수 함선 성능·모든 각도 및 장갑/시설 피해 매핑·하부 장착은 미검증이다. 기본 장면에는 시험 충돌 형상과 원본 무장을 적용하지 않았다. 다음: 실제 선체 표면을 여러 지점·방향에서 측정해 상자 후보를 생성하고, 상하/측면 실사격과 장갑 매핑·기존 OBB 대비 차이를 확인한다.

**PC14 표면 장착 실험 및 충돌상 문제 (GT):** F6 임시 레이아웃만 변경해 BF120 받침대 밑면을 측정된 선체 표면 Z=-2.551cm에 맞췄다. 장착점 Z=42→3.606cm, 발사 원점도 이동했으며 긴 임시 받침대는 시험에서만 숨겼다. ## 주요 파일과 해결한 문제

- `OVShipLayout.h/.cpp`: 슬롯/문/복도/수직 통로, 코어/함교/필수 시설 제약, 6면 구획과 무장 ID, 실제 로컬 피격 매핑. Content/Layouts의 DA_Test1Deck~3Deck 저장 완료.
- `OVShipSystemsComponent.*`, `OVSystemsTests.cpp`: 시설/장갑/무장 개체별 상태와 단일 피해 이벤트. 잘못된 레이아웃 거부, 쉴드 부분 용량 감소 재활성화, 3층 파괴의 층별 장갑 면 규칙 보완.
- `OVShip.*`: 가감속/도착/체급 선회, Hold/수동 자세, 기능 상실 이동 차단, 명시적 DEV Reset/FTL 경계 API. 기존 이동 테스트 3개 유지.
- `OVController.*`, `OVOrderInput.*`: 최신 입력, 공통 시간, 다중 선택 대표 교체 시 상세 인덱스 초기화, 완파 직후 속도/표적 제거.
- `OVHUD.*`: Canvas 수명과 독립적인 입력 영역 검사, 창 이동/리사이즈, 표시/클릭 영역 클리핑, 읽기 전용 도식. 게임 상태를 복제하거나 추가 함선을 생성하지 않음.
- `Config/DefaultGame.ini`의 Tuning은 실제 적용되는 임시 수치 프로필. `DefaultInput.ini`에 시간/명령/부대 액션.
- `Tools/CreateTestLayouts.py`: 기존 자산 보존 후 없을 때만 UE 직렬화 생성. `Tools/ValidatePhase2A.py`: 45개 실제 PIE API 검사. 이전 `ValidatePIE.py`와 1단계 증거는 역사 기록으로 보존.

## 남은 오류·미정 사항·다음 작업

1. 사용자가 [PHASE2A_GUIDE.md](PHASE2A_GUIDE.md)의 직접 조작 8단계 확인을 실행한다. 특히 창/프리뷰 위 입력 누출, Shift/RMB 고도, 부대키, 포커스 재진입을 실제 입력으로 확인한다. 실패하면 입력 순서·함선/장갑/시설 ID·F9 로그를 남긴다.
2. 한국어 엔진 시작 자체 검사 15조건 오류는 그대로 별도 유지. 프로젝트 15개 테스트 실패와 다르다. 도구/전역 언어/엔진을 임의 변경하지 않았다.
3. R11 비전투 쉴드 완충, R13 최종 키/핀 정책, R14 포탑 피해 전달은 미결정이다. 1/2층 시설 파괴의 중첩 연결 면 규칙도 임시값으로 명시했다.
4. 2B 시작 전 실제 사격/탐지/포탑 추적 요구를 최신 work와 비교한다. 기존 파일을 재작성하지 않고 이 2A 기반을 재사용한다. 2C/선내 작전/경제/저장은 이번 완료 범위가 아니다.

실행·시험 명령은 PHASE2A_GUIDE/VALIDATION에 있다. 다음 세션은 Git 상태와 이 문서의 소스 커밋을 먼저 비교하고, 이미 통과한 단계의 재구현 없이 직접 입력 잔여 확인 또는 승인된 다음 단계부터 이어간다.
