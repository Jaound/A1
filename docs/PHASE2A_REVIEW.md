> **시점 고정 기록:** 6d67970 시점 정적 검토이다. 이후 조작 보완·사용자 확인은 [구현 상태](IMPLEMENTATION_STATUS.md), 현재 규칙은 [UI](UI_SYSTEMS.md)를 따른다. 아래의 미구현/다음 작업 표시는 당시 기준이다.

## 현재 판정

**공유된 UE 소스의 2A 상태·피해·기초 조작·최소 관측 UI는 단계 기획과 대체로 일치한다. 직접 입력 검증까지 완료된 상태는 아니다.** 원격 `codex/phase1-playground`의 `6d679704be34f164bf2237609b7e1d05939d301a`를 별도 체크아웃해 정적 검토했다. 이 Linux 환경에서 UE Windows 빌드·PIE를 재실행하지는 않았다.

다음 작업은 기존 2A 보존 → 아래 입력 경계와 PlayGame3 카메라 반영 → Windows 실제 조작·기존 회귀 확인 → 2B다. 새 브랜치를 처음부터 만들 필요 없이 이미 공유된 코드 브랜치에서 이어갈 수 있다.

## 확인한 자료와 증거의 한계

- 사용자 첨부 4개 진행/검증 문서와 GitHub의 실제 `OVController`, `OVShip`, `OVOrderInput`, `OVShipLayout`, `OVShipSystemsComponent`, `OVHUD`, 자동 테스트·PIE 도구·Config를 읽었다.
- `Content`에 1/2/3층 DataAsset과 ControlRange 맵이 존재한다. 바이너리 자산 자체의 엔진 로드는 여기서 재실행하지 않았다.
- 원격 검증 기록에는 Win64 Editor `Succeeded`, 자동 테스트 15개 Success, PIE JSON 45개 passed=true가 있다. 이는 로컬 실행 기록의 내용이며 이번 환경의 재실행 결과가 아니다. 원본 전체 Saved 로그가 아니라 저장소에 선별 보존된 발췌·JSON이다.
- `379414d..6d67970`의 Source/Config/Content/Tools 차이는 없다. 후속 커밋은 문서·검증 자료만 추가했다. 보고서의 마지막 소스 커밋과 사용자 메시지의 최종 커밋은 양립한다.
- 직접 마우스·키보드는 여전히 미검증이다. 한국어 엔진 자체 검사 15건 오류는 게임 자동 테스트와 별개다.
- Godot `Play_Game_3` 카메라 기본 API 검사 12개와 경계 문제 재현은 UE의 15/45 검사에 합산하지 않는다.

## 다음 작업에서 우선 보완할 항목

### A1. UI 경계를 넘는 가운데 버튼 제스처 소유권

`OVController.cpp`의 `PlayerTick`은 현재 커서가 UI 위인지 매 프레임 판정한다. `OVHUD::HandlePointer`도 가운데 버튼의 시작 위치를 기억하지 않고 Orbit 플래그와 현재 위치만 사용한다. 따라서 전장에서 MMB를 누른 채 프리뷰로 들어가면 전장 회전이 멈추고 프리뷰가 회전할 수 있고, 반대로 나가면 전장 회전으로 바뀔 수 있는 경로가 있다.

이는 실제 OS 입력으로 재현한 결과가 아니라 소스 분기에서 확인한 경계 문제다. 버튼 press 시 전장/프리뷰의 소유자를 기록하고 release/포커스 상실까지 일관되게 전달한다. 원본의 Alt-LMB 해제 결함은 함께 가져오지 않는다.

### A2. 입력 축의 실제 배율과 FOV를 함께 확인

현재 UE는 카메라 FOV 55, `DX/DY × 0.3`, Pitch −85~−10도다. `DefaultInput.ini`에는 MouseX/Y 감도 0.07, FOV scaling 활성화, NoCapture/DoNotLock도 설정돼 있다. `GetInputMouseDelta`에 도달하기 전 엔진 처리와 실제 counts를 측정해야 한다. 소스의 0.3과 Godot의 0.32를 숫자만 비교해 감도가 거의 같다고 결론내리지 않는다.

원본은 세로 FOV 52도(16:9 수평 약 81.86도), 직접 궤도 응답, 줌 연동 pan과 보간 추적을 사용한다. UE의 실제 FOV 축 제약과 DPI를 확인하며 이식한다. 현재 어색함의 단일 원인을 아직 확정하지 않는다.

### A3. API 검사는 실제 입력 경로를 지나지 않음

`ValidatePhase2A.py`의 카메라 pan/orbit/zoom 검사는 카메라 속성을 설정한 뒤 `update_camera()`를 부른다. 창 검사는 `handle_pointer()` API를 직접 호출한다. 따라서 45/45는 마우스 캡처·상대 이동량·버튼 해제·UI 경계 통과를 증명하지 않는다. 사용자 조작 피드백은 이 미검증 경로를 실제로 확인해야 한다는 근거다.

### A4. 충돌 기초와 시험 예외를 최종 기능으로 확대하지 않기

`ResolveContacts`는 구형 반경 기반이며 양쪽 이동 불가 시 분리하지 않는다. 정밀 함체 충돌·체급 우선권·충각·모든 배치의 겹침 방지 완료가 아니다. 자산 로드 실패 시 메모리 fallback이 있고, DEV `ResetState`는 완파도 초기화한다. 새 체크아웃의 자산 존재 검사를 유지하고 DEV 초기화를 실제 수리로 보고하지 않는다.

### A5. 임시 밸런스와 카메라 스케일 분리

시험 함선 엔진 3기 정상 효율은 200%다. 기본 850/420cm/s와 실제 효율 적용 속도를 구분하고 프로토타입 m/s와 비교해 50% 감소를 다시 곱하지 않는다. 함선 기동을 바꾸지 않고 카메라 거리·pan·근접 한계를 단일 스케일로 보정한다.
