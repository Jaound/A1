# Play Game 3 조작 분석과 UE5 이식안

> **시점 고정 기록:** be544d7 이전 원본 분석·이식 계획이다. 이후 조작 보완·사용자 확인은 [구현 상태](../03_development/IMPLEMENTATION_STATUS.md), 현재 규칙은 [UI](../01_design/interface/UI_SYSTEMS.md)를 따른다. 아래의 미구현/다음 작업 표시는 당시 기준이다.

> 사용자 요청: 다음 작업에서 `Play_Game_3`의 편한 조작감을 가져온다. **원본 분석·프로필 추출은 완료**, UE `6d67970` 소스까지 비교했으며, 실제 카메라 변경은 다음 로컬 작업에 적용할 명세로 남겼다. 카메라 수치·동작과 이식 시 보정/개선안을 구분한다.

## 1. 실제로 확인한 소스와 검증 방법

- 원본 카메라: `Play Game/src/view3d/RtsCameraRig.gd` 38~66행(마우스), 69~108행(키보드·추적), 110~121행(기준점 궤도).
- 전장 명령: `SpaceViewport.gd` 184~351행. UI 전달: `MainGame.gd` 503~574행. README 설명만 믿지 않고 실제 분기를 확인했다.
- 원본은 Godot 4.3용이라고 명시한다. 여기서는 설치된 **Godot 4.6.3 headless**로 원본 카메라 이벤트/API 기본 동작 **12개 통과**를 확인했다. 실마우스·그래픽 렌더·UE 실행 검증은 아니다.
- 별도 경계 검사에서 **Alt를 먼저 놓고 LMB를 해제하면 회전이 계속되는 원본 문제**를 재현했다. 정상 12개 검사 성공과 이 관찰을 구분한다.
- 출처 해시, 원본 카메라, 입력 발췌, 프로필과 결과는 [참조 자료](../../reference/PlayGame3Controls/README.md)에 보관한다. `.godot` 캐시나 다른 게임 시스템을 UE 프로젝트에 복사하지 않는다.

## 2. 조작감의 핵심 — 원본의 실제 동작

| 항목 | 확인한 원본 동작 | 현재 UE 안내와의 차이 |
| --- | --- | --- |
| 가운데 버튼 드래그 | **현재 카메라 기준점(Pivot)을 중심으로 궤도 회전**, 거리 유지 | UE도 CameraFocus 궤도 회전, DX/DY×0.3, Pitch −85~−10° |
| Alt+왼쪽 드래그 | 같은 궤도 회전의 대체 입력 | 현재 가이드에 없음 |
| 가로 마우스 감도 | 원본 yaw `−0.32°/참조 px` | UE 축으로 변환 후 회전 방향 검사 필요 |
| 세로 감도 | 내려다보는 각도 `+0.28°/참조 px`, 12~84° 제한 | 반전·축·프레임 시간 중복 확인 필요 |
| 휠 | 현재 거리 ×0.88(가까이) / ×1.13(멀리) | 현재는 명령 중 휠이 고도 조정에 쓰임 |
| WASD·방향키 | 카메라 yaw 기준 수평 이동, 대각선 정규화 | 원본은 줌 거리별 이동 속도도 조절 |
| 이동 속도 | `180 × clamp(거리/240, 0.45, 2.5)` 원본 단위/초 | UE 임시 시험장 스케일에 보정 필요 |
| Q/E | 연속 좌우 회전 75°/s | 현재 UE 가이드는 Q/E가 고도 이동 |
| F 추적 | 최초 선택 함선 위치로 기준점 이동 후 지속 추적. 추적 중 `lerp α=min(1,실시간 Δt×10)` | UE는 매 프레임 함선 위치에 기준점을 즉시 대입 |
| 추적 해제 | WASD/방향키 평면 이동 입력 시 해제 | UI·포커스 상태도 함께 검사 |
| 휠 최소 거리 | `max(35, 선택 일반 함선 half_extents 길이×1.45)` | VFX/선택 표시를 포함한 ActorBounds로 바꾸면 줌이 튈 수 있음 |
| 기본 시점 | 원본 yaw −32°, 고도각 38°, 거리 290, 최소/최대 35/680 | 거리 숫자를 그대로 UE cm로 넣지 않음 |

원본 회전은 마우스 입력 즉시 각도에 반영하며 **별도 마우스 회전 보간은 없다.** 느린 추가 보간을 넣는 것이 원본을 재현하는 방법은 아니다. 부드러운 추적 보간과 직접 회전 응답을 구분한다. 선택만 바꾼다고 기준점이 반드시 함선으로 옮겨지는 것은 아니고 F 추적이 그 역할을 한다.

## 3. FOV는 숫자만 복사하면 달라짐

원본 `Camera3D.fov=52`, keep_aspect=1이다. 1600×900 headless 투영 검사에서 **세로 52.00°, 가로 81.8558°**를 확인했다. UE 카메라에 수평 FOV 52를 그대로 넣으면 더 좁게 보인다.

세로 FOV를 보존하는 투영 목표는 다음과 같다.

```text
HorizontalFOV = 2 × atan(tan(VerticalFOV / 2) × ViewportAspect)
VerticalFOV = 52°
```

UE5 카메라의 실제 AspectRatioAxisConstraint와 FOV 적용 코드를 확인한 뒤 최종 화면에서 맞춘다. 초광폭·4:3·창 크기 변경 때도 투영과 입력 광선이 같은 실제 전장 뷰포트를 사용해야 한다. 현재 UE는 `SetFieldOfView(55)`와 전체 뷰포트를 사용한다. 카메라의 실제 FOV 축 제약은 엔진/로컬 플레이어 설정까지 확인해야 하므로 55를 곧바로 세로각으로 해석하지 않는다. 이것만으로 어색함의 원인을 단정하지 않는다.

## 4. UE5 좌표와 시간 적용

- 원본은 Y-up·Z 방향 카메라다. UE는 Z-up·+X 전방이다. 예시 좌표 변환 `UE(X,Y,Z)=(-원본Z, 원본X, 원본Y)`를 사용하면 원본 회전 수치를 일관되게 옮길 수 있다.
- 이 변환에서 카메라가 보는 UE yaw는 원본 yaw의 음수다. 즉 가로 드래그는 UE 시선 yaw에 `+Δx×0.32°`, 고도각은 `+Δy×0.28°`에 해당한다. UE Pitch는 내려다보는 각도의 음수다. 기존 프로젝트의 축을 먼저 확인하며 Rotator에 원본 값을 무조건 복사하지 않는다.
- 픽셀 델타에는 Δt를 다시 곱하지 않는다. 키보드 연속 회전·평면 이동·추적에는 실제 시간 Δt를 적용한다. 게임 배속을 카메라에 적용하지 않는다.
- DPI·Slate 논리 픽셀·원시 마우스 counts 중 무엇을 받는지 명시한다. 원본의 캔버스 배율과 UE 입력 배율을 맞추지 않으면 동일 숫자라도 감도가 달라질 수 있다.
- 거리·pan 속도·근접 한계는 단일 `WorldUnitsPerReferenceUnit` 또는 기준 함선 크기 비율로 변환한다. 단순 m→cm는 100이지만 현재 시험장 메시가 같은 실제 크기라고 보장되지 않는다. 먼저 같은 함선 화면 점유율을 맞추고 거리·평면 이동을 함께 보정한다. 함선의 실제 기동·전투 수치를 카메라 보정을 위해 바꾸지 않는다.

## 5. 우클릭 이동도 동작이 다름

원본은 우클릭을 누른 위치의 평면 목적지를 고정하고, 드래그로 고도만 바꾼 뒤 **버튼을 놓을 때 한 번 확정**한다. 고도 감도는 `0.55 원본 단위/px`, 범위 ±180, 일반 임계값 8px다. 적함에서 시작한 짧은 우클릭은 25px까지 표적 지정을 우선하며 Shift는 강제 이동, Ctrl은 방향 지정이다.

현재 UE 안내는 XY→Z→XY를 조정한 뒤 Enter/좌클릭으로 확정한다. 단순 감도 차이가 아니라 **입력 확정 방식 차이**다. 다음 로컬 작업은 `PlayGame3` 프리셋에서 RMB release 확정을 제공하고 기존 V/Enter 정밀 입력은 별도 경로로 보존하는 안을 권장한다. 두 경로가 같은 release/click을 중복 소비해 명령을 두 번 발행하지 않게 한다.

원본 SpaceViewport는 카메라에 입력을 먼저 전달하므로 이동 드래그 중에도 휠은 카메라 줌이다. 따라서 새 프리셋에서 휠을 고도 조정에 동시에 쓰지 않는다. 원본의 0.55 감도·±180 범위는 함체/월드 보정 후 적용하며 기존 UE 시험 범위를 무단 확대하지 않는다.

## 6. 함께 고칠 경계와 원본에서 가져오지 않을 것

1. **Alt-LMB 해제 오류:** 원본은 release 시 Alt가 유지돼야 분기를 통과한다. 포인터 제스처를 시작한 버튼을 기억하고, Alt 해제·버튼 release·포커스 상실 시 확실히 종료한다.
2. **휠 왕복 비대칭:** 0.88×1.13=0.9944로 왕복할 때 조금씩 가까워진다. 첫 이식은 원본값을 프로필로 보존하되 상호 역수 줌은 별도 선택 사항으로 둔다.
3. **UI/포커스:** 실제 창·프리뷰 위에서 시작한 드래그는 그 창만 조작한다. 전장에서 시작한 제스처는 포인터 소유권을 유지하며 종료를 놓치지 않는다. 복귀 첫 프레임의 누적 마우스 델타는 버린다.
4. **키 충돌:** 원본의 R/C 고도 이동을 그대로 복사하면 R 수리와 충돌한다. 우선 마우스 회전·줌·평면 이동·추적을 이식하고, Q/E 회전 도입 시 고도 이동 키와 기존 Z/C 보조키를 함께 재배치한다. PageUp/PageDown 고도는 대안이며 아직 확정 기본키로 쓰지 않는다.
5. **불일치 미리보기:** 원본은 8px 미만에서 현재 커서 교점을 표시하지만 실제 확정점은 누른 순간의 고정 XY다. UE에는 표시 목적지와 확정 목적지를 같은 값으로 연결한다.
6. **게임 규칙은 이식 대상 아님:** 원본에는 보장 근거리 185와 포드 거리 240 등 현재 기획과 다른 임시값도 있다. 카메라 편의 때문에 SectorSim·전투 밸런스·시설 규칙 전체를 대체하지 않는다.

## 7. 실제 UE 소스 비교 기준

비교 대상은 `codex/phase1-playground`의 `6d67970`이다.

| 동작 | 현재 UE 소스 | 이식 목표 |
| --- | --- | --- |
| 평면 이동 | `CameraDistance × 0.45 × 실제 Dt` | 원본의 하한/상한이 있는 줌 연동 속도를 스케일 보정 |
| 추적 | 선택 함선 위치를 매 프레임 즉시 대입 | 원본 `min(1,Dt×10)` 보간 비교 |
| 휠 | 거리 ×0.86 또는 역수, 1200~16000cm. 이동 모드에서는 고도 ±250 | PlayGame3 프로필에서 항상 카메라 줌 |
| 우클릭 해제 | 적함 짧은 클릭 표적만 확정, 이동은 좌클릭/Enter 별도 | PlayGame3 프로필에서 이동도 release 한 번 확정 |
| 입력 배율 | MouseX/Y Sensitivity 0.07, FOV scaling 활성, NoCapture | OS→엔진→GetInputMouseDelta 배율을 실측 후 감도 결정 |
| 회전 입력 소유 | 현재 커서 위치의 OverUI로 매 프레임 전환 | press 시 소유자 고정, release/포커스 상실 정리 |

`ValidatePhase2A.py`의 카메라 검사는 속성 변경과 `update_camera()` 호출이다. 실제 `PlayerTick` 입력을 검사한 결과로 해석하지 않는다. 관련 정적 검토 결과는 [2A 검토](../archive/analysis/PHASE2A_REVIEW.md)에 있다.

## 8. 다음 로컬 작업의 완료 기준

- 최신 UE 소스와 코드 커밋을 확인하고, 2A 상태·피해·레이아웃을 재작성하지 않는다. 카메라/입력/키 설정/표시 설명의 변경을 별도 체크포인트로 만든다.
- 현재/PlayGame3 프로필을 비교할 수 있게 하고 변경한 실제 감도·FOV·거리 스케일을 기록한다. 플레이어는 기본 카메라만 조작해도 피벗·거리·상하 한계를 예측할 수 있어야 한다.
- 30/60/144 FPS에서 같은 총 마우스 이동의 각도가 같고, 1/2/3배속·일시정지에서 카메라 감각이 같아야 한다. UI 위 조작이 실제 함선 자세·목적지를 바꾸면 안 된다.
- Alt를 먼저 놓는 경우, 창 밖 release, 포커스 상실·복귀, 줌 최소/최대, F 추적 중 선택 해제·함선 파괴를 검사한다.
- RMB release 이동의 목적지·횟수, 적 우클릭 표적 우선, Shift 강제 이동, Ctrl 방향, 취소·프리뷰/UI 경계를 실제 마우스로 확인한다.
- 기존 15개 자동 테스트·45개 PIE API 검사와 새 입력 회귀를 유지한다. API와 실제 입력 성공을 분리하고 실패하면 입력 순서·프레임률·프로필·해상도와 F9 로그를 남긴다.
- 원본 카메라에 대해 여기서 수행한 12개 API 검사는 참고 구현 확인일 뿐이며, 이 절차의 UE/실마우스 통과를 대체하지 않는다.
